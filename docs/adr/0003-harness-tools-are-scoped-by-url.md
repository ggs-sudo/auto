# Harness tools are served from a hand-written in-process endpoint, scoped by URL

ADR-0002 moved the tools to the orchestrator agent; this is how they are served. Each ephemeral invocation gets an **inline, strict** MCP config whose **URL carries the run and the node under judgment**, and the endpoint only answers on addresses that have an open intervention. No tool takes a node argument, so an agent cannot act on a node it was not invoked about — the address that would let it do so does not exist. That is enforcement by addressing rather than validation of something the agent supplies, which matters because the agent's judgment is the one part of the system nothing can verify until it runs live.

The transport is a small hand-written streamable-HTTP endpoint on `http.server` rather than the MCP SDK. The SDK would bring an ASGI stack and its session manager for two tools, and per-request URL scoping fights its design; the JSON-RPC surface an ephemeral one-turn agent needs is `initialize`, `tools/list` and `tools/call`, answered with `application/json`, which the transport allows for a request that gets a single response. The cost is an unverified assumption — that the CLI's MCP client is content without an event stream — recorded in the README rather than designed around.

## Consequences

- **An intervention's window is its lifetime.** The URL is registered while the agent runs and deregistered when it ends, so a process that outlives its intervention has nowhere to send a call. The same registry makes "interventions on one node never overlap" structural: a second window on an open node is refused.
- **Requests cross a thread and one invariant holds anyway.** The endpoint serves on its own threads; every tool call is handed to the loop thread before it touches anything, which is the same thread every run-directory write happens on. The single-writer guard catches a violation rather than trusting care.
- **Mutual exclusion lives in the tool layer.** `send_to_session` and `complete_node` are exclusive per invocation and the second is refused with a reason the agent can read. A refused call is recorded, not dropped: what the agent tried and was not allowed to do is the interesting half of a surprising decision. A tool that could not do its job has not used the invocation up.
- **The agent is held to an allowlist, not a bypass.** Driven sessions bypass permissions, for the reason ADR-0002 records; the orchestrator agent gets the two harness tools plus `Read`, `Glob` and `Grep` and nothing else. The answer policy tells it the target repo's docs outrank the interviewer, so it must be able to read them — but "an agent that rambles cannot corrupt state" has to be a fact about what it can do, not a line in its prompt, and "the orchestrator never writes a tracker file itself" needs a mechanism rather than an intention.
- **No dependency was added.** The harness stays `click` and `pydantic`, and the tool path is covered by tests that speak real JSON-RPC over real HTTP — including one that drives a whole run through real subprocesses.
